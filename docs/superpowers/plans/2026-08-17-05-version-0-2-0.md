# Layup 0.2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The last build anyone installs by hand. It fixes the three things that broke the first real pairing session, adds the in-call controls that session showed were missing, asks for permissions before a call rather than during one, and updates itself from `layup.blah.au` from then on.

**Architecture:** Auto-update via `electron-updater` against a generic provider on the existing Caddy host — which needs a `zip` target beside the `dmg`, because Squirrel.Mac updates from zip. Updates never install during a live layup. The two P0 bugs are both in `LayupRoom.tsx` and are fixed at the root: one shared capture instance, and a picker that overlays rather than replaces the room. Device switching uses `RTCRtpSender.replaceTrack` so changing your microphone never renegotiates the peer connection — renegotiation is precisely what kills a call.

**Tech Stack:** Electron 43, electron-builder + electron-updater, React 19, TypeScript, Go 1.26.4.

**Spec:** `docs/superpowers/specs/2026-08-17-two-person-dogfood-design.md` (this plan extends it; where they conflict, the field report in the PR wins)

## Global Constraints

- **Never renegotiate to change a device.** Use `RTCRtpSender.replaceTrack`. A renegotiation mid-call is what this release exists to stop causing.
- **Never install an update during a live layup.** Download silently, apply on quit or on explicit user action.
- All existing tests pass. `make check` green. `make test-boundary` → `BOUNDARY OK`; every new preload channel goes in the fixture, and no assertion is weakened.
- Never log the bearer token.
- Version is `0.2.0`. The git SHA is baked in at build time and shown in the UI — when a tester says "it's broken", we must know exactly what they ran.
- **Do NOT run `npm run test:smoke`** — 5 pre-existing failures, bisected to before this work.
- macOS only for now; guard platform-specific code rather than assuming.

### Task 3: Fix — clicking a source actually shares it

**Root cause (already established, do not re-investigate):** `LayupRoom.tsx:46` creates its own `useLocalCapture()` instance which **never calls `refresh()`**, so `capture.sources` is permanently `[]`. `CapturePicker.tsx:21` creates a *second, independent* instance that does refresh, so the user sees thumbnails. `startSharing` (`LayupRoom.tsx:82`) then does `capture.sources.find(...)` against the empty array, gets `undefined`, and returns silently at line 83. Every click. No error.

**Files:** Modify `apps/desktop/src/renderer/layup/LayupRoom.tsx`, `apps/desktop/src/renderer/capture/CapturePicker.tsx`, and their tests.

- [ ] **Step 1: Write the failing test.** Render the room, open the picker, click a source, and assert `window.layup.share.start` was called with that source id. **This must fail against current code** — that is the proof it reproduces the reported bug.
- [ ] **Step 2: Run it, watch it fail.** Confirm the failure is "not called", not a crash.
- [ ] **Step 3: Fix at the root — one capture instance.** Lift capture state so the picker and the room share it: have `LayupRoom` own the `useLocalCapture()` instance and pass `sources` / `refresh` / `error` down to `CapturePicker` as props, rather than the picker creating its own. Keep `CapturePicker` usable standalone (its existing test renders it alone) by letting it fall back to its own instance when no sources prop is given — but the room must pass one.
  - Do **not** "fix" this by having `LayupRoom` also call `refresh()`. Two instances enumerating sources independently is the defect; one of them going stale is just the symptom that surfaced.
- [ ] **Step 4: Guard the silent failure.** If a picked source cannot be resolved, surface an error to the user instead of `return`. A silent early return is what made this cost a whole session to notice.
- [ ] **Step 5: Verify.** New test passes; all existing tests pass.
- [ ] **Step 6: Commit.** `git commit -m "desktop: one list of sources, so picking one shares it"`

### Task 4: Fix — opening the picker no longer kills audio and video

**Root cause (already established):** `LayupRoom.tsx:212` is `if (mode === 'picker') return (...)`, an early return rendering the picker **and nothing else**. `FaceTiles` (line 311) lives in the main return and holds the `<video>` elements — the remote ones unmuted, i.e. they *are* the audio output. Opening the picker unmounts them, so the media stops. The window choice is irrelevant; opening the picker at all does it.

**Files:** Modify `apps/desktop/src/renderer/layup/LayupRoom.tsx` and its tests; `apps/desktop/src/renderer/styles.css`.

- [ ] **Step 1: Write the failing test.** Render the room with a remote participant, open the picker, and assert the remote media element is **still mounted**. Assert the same element instance survives (not just that one exists) — remounting would restart the stream even if a node is present.
- [ ] **Step 2: Run it, watch it fail.**
- [ ] **Step 3: Fix at the root.** Make the picker an **overlay on top of the room**, not a replacement for it. `FaceTiles` and the media elements stay mounted continuously for the whole life of the layup, in every mode. Restructure so the mode changes what is *layered over* the room, never whether the room exists.
- [ ] **Step 4: Check the other early returns.** `mode === 'compact'` (line 233) also returns a different tree. Verify it does not unmount media either; if it does, fix it the same way and say so in the report.
- [ ] **Step 5: Verify.** New tests pass; all existing pass; `make test-boundary` green.
- [ ] **Step 6: Commit.** `git commit -m "desktop: the picker floats over the call instead of replacing it"`

- [ ] **Step 4: Make the invite reachable regardless of window size.** The compact window is 380×620 and the invitation renders above `HappeningNow` and `PeopleGrid`. Ensure an incoming invitation is always visible and its buttons reachable — pin it to the top, and grow or scroll rather than clip.

### Task 9: Ask for permissions before the call, not during it

Today `main/permissions.ts` handles Screen Recording well — status, plain-language guidance, a deep link to the right settings pane — and there is **no equivalent for Camera, Microphone or Accessibility**. Accessibility is the one whose absence makes remote control fail silently, which the helper's own source calls the worst available outcome.

**Files:** Modify `apps/desktop/src/main/permissions.ts` + test; create `apps/desktop/src/renderer/onboarding/Permissions.tsx` + test; modify `App.tsx`, `shared/ipc.ts`, `preload/api.ts`, `main/ipc.ts`, `test/boundary/main.cjs`.

**Interfaces:** `PermissionService.all(): Record<'camera'|'microphone'|'screen'|'accessibility', PermissionState>` where each is `{ status, ok, guidance, canOpenSettings }`; `request(kind)` and `openSettings(kind)`.

- [ ] **Step 1: Write the failing tests.**
  - all four permissions are reported, each with plain-language guidance naming Layup;
  - camera and microphone can be *requested* in-process (`systemPreferences.askForMediaAccess`), which actually shows the OS prompt;
  - screen recording and accessibility **cannot** be requested programmatically — they must deep-link to the correct settings pane, and each pane URL is asserted exactly;
  - accessibility status comes from the **helper's own `AXIsProcessTrusted` report**, not a guess, because the helper is the process that will post the event;
  - a non-macOS platform reports `not-required` rather than pretending.
- [ ] **Step 2: Run, watch fail.**
- [ ] **Step 3: Implement the service.** Extend `permissions.ts` following its existing shape exactly. Accessibility reads `HelperState.capabilities` from `helper-supervisor.ts`.
- [ ] **Step 4: Build the screen.** After registration, if anything is missing, show a Permissions screen: one row per permission with its status, what it is for in one line, and a button that either triggers the OS prompt or opens the right settings pane. Skippable — but reachable any time from the footer, because Screen Recording needs an app restart and people will come back to it.
- [ ] **Step 5: Warn where it actually bites.** In `RemoteControlPanel`, if Accessibility is missing, show the guidance and an Open Settings button **instead of** a switch that appears to work and does nothing.
- [ ] **Step 6: Verify.** All tests pass; `make test-boundary` → `BOUNDARY OK` with the new channels in the fixture. Check by hand on a machine with permissions revoked that each button lands on the correct pane.
- [ ] **Step 7: Commit.** `git commit -m "desktop: ask for what we need before the call starts"`

### Task 11: The window drags from the title bar

**Reported:** "the app bar with the traffic lights doesn't move the window, only dragging the Layup header moves it."

**Root cause (established):** `main/index.ts:540` uses `titleBarStyle: 'hidden'` with

content and the app must supply its own drag region. It supplies only two:
`shell__header` (`App.tsx:110`) — which does not exist in the layup room or on the
Add-server screen — and `call__stage` (`CompactBar.tsx:44`). The strip behind the
traffic lights is not a drag region in any view.

**Files:** modify `apps/desktop/src/renderer/styles.css`, `App.tsx`, `LayupRoom.tsx`,
`onboarding/AddServer.tsx`, `onboarding/Permissions.tsx`.

- [ ] **Step 1: Write the failing test.** Assert a top drag strip is present in every
  top-level view — Add-server, Permissions, home/People, and the layup room in each
  mode. Assert it carries the drag affordance and that interactive children inside it
  are marked `no-drag`.
- [ ] **Step 2: Run it, watch it fail.**
- [ ] **Step 3: Fix at the root.** One always-present drag strip spanning the full
  window width at the top, tall enough to cover the traffic lights (they sit at y=12),
  rendered by the shell rather than by each view — so a new screen cannot forget it.
  Existing `.drag` usages stay, but nothing should depend on a particular view
  supplying the title-bar drag region.
- [ ] **Step 4: Do not break clicking.** Every button, input and link inside the strip
  must be `no-drag`, or it becomes unclickable. Verify the traffic lights themselves
  still work — they are OS-drawn and must not be covered by a `no-drag` element.
- [ ] **Step 5: Verify by hand** in a real window, in every view, including the

## Done when

- Clicking a window in the picker shares that window.
- Opening the picker does not interrupt audio or video.
- An incoming invitation is visible, audible, and either joins or says why it could not.
- Route and RTT are visible during a call, and correctly say "Relayed" when relay is forced.
- Microphone, camera and speaker can be changed mid-call without dropping it.
- Permissions are requested and shown before a call, with Accessibility read from the helper itself.
- The window drags from the title-bar strip in every view.
- 0.2.0 is installed by hand once, and 0.2.1 arrives on its own.
