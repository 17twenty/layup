# PLAN-1.5 - Server-local identity and People bootstrap

**Status: LOCKED UNTIL PLAN-1 GATE READY**

This is a mandatory product-model correction to be executed **after PLAN-1 reports `PLAN-1 GATE READY` and before PLAN-2 is reviewed or unlocked**.

It exists because the People surface needs an explicit answer to a basic question: **how does somebody become one of your People?**

PLAN-1.5 does not add federation, enterprise identity, SSO, contact sync, channels, chat, or a global social graph. It adds the smallest server-local identity and mutual People relationship model needed for the People-first product to make sense.

## Product principle

> A Layup server is its own social universe.

Users have an immutable identity on one server. People relationships exist only between users on that same server. There is no cross-server lookup, presence, relationship, signalling, or federation protocol.

If somebody is not on your server, **invite them to your server**. Once they join, they receive a new identity local to that server and can then be added to People like anybody else.

The same human may therefore have unrelated identities on multiple Layup servers. Layup does not attempt to prove, merge, or federate those identities.

## Hard non-goals

Do not add:

- cross-server federation;
- ActivityPub, Matrix, XMPP or another federation protocol;
- globally unique user handles;
- cross-server presence;
- cross-server People relationships;
- account linking across servers;
- automatic identity merging;
- remote-server discovery;
- a central Layup cloud directory;
- Slack/Teams/Google contact sync;
- OIDC/SAML directory provisioning;
- persistent chat or messaging;
- teams/channels/groups as a social model.

A URL pointing at another Layup server is simply a URL to **that server**. It is not federation.

# 1. Server-local identity

Every user has an immutable opaque ID generated by the server.

Example:

```text
usr_01k...
```

The exact encoding is an implementation detail, but IDs MUST:

- be opaque;
- be stable for the lifetime of that user on that server;
- never be recycled;
- be generated server-side;
- not contain email addresses or other personal data;
- not be treated as globally resolvable identifiers.

A User may also have:

```text
Display name: Nick Glynn
Handle:       @nick
User ID:      usr_01k...
```

The handle is server-local and human-friendly. It MAY be changeable later.

The immutable User ID is authoritative.

## Identity invariant

```text
server A / usr_123 != server B / usr_123
```

Layup MUST NOT implement code that attempts to resolve or relate these identities across servers.

---

# 2. Server membership and invitation

A person who does not yet belong to a Layup server can be invited to that server.

For PLAN-1.5, a server invitation is represented by an opaque, revocable token generated by the server.

Conceptually:

```text
ServerInvite
├── id
├── token_hash
├── inviter_user_id
├── expires_at
├── max_uses
├── uses
├── revoked_at
└── created_at
```

PLAN-1.5 may use the existing development identity mechanism rather than implementing production account creation, but the domain and flow must make the eventual boundary clear.

Organisation/server policy will later decide who may create invitations. PLAN-1.5 may use a simple configuration switch.

## Invite behaviour

The intended user journey is:

```text
Nick
  -> Copy invite link
  -> sends URL to Alice

Alice opens URL
  -> target Layup server is identified by the URL itself
  -> if Alice is already a member, continue
  -> otherwise join/create a server-local identity through the available PLAN-1.5 dev flow
  -> arrive on Nick's profile
  -> "Add Nick to People?"
```

Joining the server MUST NOT silently create a People relationship.

The recipient must still consent to the mutual People relationship.

An invite URL does not identify or connect to Alice's existing identity on another Layup server.

## Suggested route

```text
https://layup.example/i/<opaque-invite-token>
```

The token should retain enough server-side context to return the new member to the inviter's profile after successful server join.

# 3. Profiles

Every server-local user has a small profile surface.

Minimum fields:

- display name;
- optional server-local handle;
- immutable User ID with copy affordance;
- avatar/initials if already supported;
- People relationship state;
- `Add to People` / `Request pending` / `Remove from People` action as appropriate.

For an existing server member, a profile can be addressed by an ordinary server-local URL:

```text
https://layup.example/p/usr_01k...
```

This profile route **does not itself grant server membership**.

If an external person needs access, use a server invite URL instead.

---

# 4. People is a mutual relationship

The People screen is not the organisation directory.

A user appearing in another user's People list requires a mutually accepted relationship.

Internally use a first-class relationship object such as `PeopleConnection`.

Conceptually:

```text
PeopleConnection
├── id
├── requester_user_id
├── recipient_user_id
├── state
├── created_at
├── responded_at
└── ended_at
```

Minimum states:

```text
PENDING
ACCEPTED
DECLINED
CANCELLED
REMOVED
```

`BLOCKED` may be reserved in the domain for later use, but PLAN-1.5 does not need a full abuse-management UI.

## Relationship invariants

An accepted connection is mutual:

```text
Nick sees Karl
Karl sees Nick
```

Do not create two independent follow records.

Only one active/pending relationship may exist for an unordered pair of users.

Removing an accepted connection ends it for both users.

A request may be cancelled by its requester while pending.

A recipient may accept or decline.

A duplicate pending request must resolve to the existing request rather than generating notification spam.

---

# 5. Same-server directory

Users need a way to find somebody who is already on the same server without automatically adding the entire organisation to People.

Add an `Add someone` / People search surface.

Search may match:

- display name;
- server-local handle;
- exact immutable User ID.

Directory results expose only enough information to identify the person and request a People relationship.

Example:

```text
Add someone
────────────────────────
Search name, @handle or ID

Karl Smith
@karl
usr_01k...
[Add to People]
```

Exact User ID lookup must work even when fuzzy name search is disabled later by enterprise policy.

For PLAN-1.5, directory search is same-server only.

# 6. Presence privacy

This addendum intentionally changes the broad PLAN-1 assumption that organisation members receive one another's normal presence by default.

## Accepted People

Accepted People may receive the normal presence/activity model already defined by PLAN-1:

```text
AVAILABLE
AWAY
DND
OFFLINE
```

plus permitted coarse activity:

```text
not in layup
in private layup
in open layup
```

Private layup details remain redacted.

## Same-server stranger

A same-server user who is NOT an accepted Person may be discoverable through directory search but does not automatically receive normal personal presence.

They may see directory identity fields such as:

- display name;
- handle;
- avatar/initials.

They should not automatically learn:

- online/offline status;
- Away/DND;
- private layup activity;
- private layup title;
- private participant list.

## Open layups

Open layups are a separate discovery surface.

An organisation-visible open layup may expose the room metadata allowed by its visibility policy, including participant identities, even where a viewer is not connected to those participants as People.

Seeing somebody in an open layup does not create a People relationship and does not grant general presence visibility after the layup disappears.

---

# 7. People home grid

The primary People grid is populated from **accepted PeopleConnection relationships**, not from the raw organisation directory.

This means a new user's home screen may legitimately begin empty.

Provide an obvious affordance such as:

```text
Your People

No one here yet.

[Add someone]   [Invite someone]
```

`Add someone` searches the existing same-server directory.

`Invite someone` creates a server invitation link for somebody not yet on this server.

Pending incoming People requests should be visible without turning the product into a messaging inbox.

---

# 8. Discovering People through layups

A shared Layup is a first-class social discovery mechanism.

Clicking a participant who is not already one of your People should expose:

```text
Alice Chen
@alice

[Add to People]
```

The normal People request lifecycle applies.

Do not auto-connect users merely because they shared a layup.

This must work for a user who originally joined the server through an invitation link: once they possess a server-local identity, they are an ordinary same-server user for People purposes.

---

# 9. Link taxonomy

Keep these concepts distinct.

## Layup link

```text
/l/<token-or-id>
```

Purpose: join or request access to a layup according to its visibility rules.

## Profile link

```text
/p/<user-id>
```

Purpose: show a profile to somebody already authorised on this server.

Does not grant server membership.

## Server invite link

```text
/i/<opaque-token>
```

Purpose: admit/invite somebody to this Layup server and return them to the inviter context.

The server invite flow may end by presenting:

```text
You joined Acme Layup.

Nick invited you.
[Add Nick to People]
```

Do not overload a layup link with permanent server/social semantics.

---

# 10. Control-plane boundary

The Go control plane owns:

- server-local users;
- server invitation tokens;
- directory lookup;
- People requests/connections;
- profile lookup;
- People-scoped presence subscription/fan-out;
- relationship events.

WebRTC remains uninvolved in identity/directory/People relationships.

Do not send People requests over a WebRTC data channel.

---

# 11. Realtime events

Add control-plane events/commands conceptually equivalent to:

```text
people.requested
people.accepted
people.declined
people.cancelled
people.removed

profile.updated

server_invite.created
server_invite.revoked
server_invite.consumed
```

Presence fan-out should be recalculated when a People relationship becomes accepted or removed.

On acceptance, the two users should begin receiving permitted realtime presence without requiring an application restart.

On removal, presence delivery should stop promptly.

# 12. Canonical product journeys

## Journey A - Add existing server user by ID

```text
Alice starts with an empty People list
  -> Add someone
  -> paste Bob's User ID
  -> Bob profile resolves
  -> Add to People
  -> Bob receives request
  -> Bob accepts
  -> Bob appears in Alice's People grid
  -> Alice appears in Bob's People grid
  -> permitted presence begins flowing
  -> Alice clicks Bob
  -> ordinary PLAN-1 invite-to-layup flow begins
```

## Journey B - Invite someone who is not on the server

```text
Nick
  -> Invite someone
  -> Copy server invite URL
  -> sends URL to Alice

Alice
  -> opens URL
  -> joins the target Layup server through available identity flow
  -> receives a new User ID local to that server
  -> lands on Nick's profile
  -> Add Nick to People
  -> Nick accepts
  -> mutual People relationship exists
```

## Journey C - Add somebody you met in a layup

```text
Nick joins open layup
  -> meets Alice
  -> clicks Alice participant card
  -> Add to People
  -> Alice accepts
  -> they become mutual People
```

# 13. Required regression changes to PLAN-1

PLAN-1.5 supersedes these PLAN-1 behaviours where they conflict:

### P1-0104 - Development user and organisation directory

Keep deterministic users, but the directory is a **search/discovery source**, not the People list.

### P1-0107 - Presence publication and fan-out

Change from organisation-wide normal presence fan-out to **accepted-People-scoped presence fan-out**, plus separate open-layup discovery events.

### P1-0108 - People home grid

Change from directory-backed People tiles to **accepted PeopleConnection-backed tiles**.

### Phase C interactions

Click-to-layup actions operate primarily on accepted People. Directory results expose `Add to People`, not the full People-tile interaction model.

Open layup discovery remains organisation scoped according to the room visibility policy.

---

# 14. PLAN-1.5 exit gate

PLAN-1.5 is complete only when this flow passes end-to-end on two clients:

```text
Alice and Bob are on the same server
Alice and Bob are not People
Alice cannot see Bob's normal presence

Alice finds Bob by exact User ID
Alice sends Add to People
Bob accepts

Alice immediately sees Bob in People
Bob immediately sees Alice in People
permitted presence begins flowing both ways

Alice clicks Bob
Bob receives "Alice wants to start a layup"
Bob accepts
both enter the same logical layup
```

And this external bootstrap flow is demonstrated with the available PLAN-1.5 development identity mechanism:

```text
Nick creates server invite
new user consumes invite
new server-local User identity exists
new user lands in inviter context
People relationship is NOT automatic
Add to People can then be requested normally
```

Finally verify:

- no cross-server lookup exists;
- no cross-server People relationship exists;
- no organisation-wide personal presence leak remains;
- People grid is connection-backed;
- shared layup participant can be added to People;
- removal stops mutual People presence.

When complete, write:

```text
PLAN-1.5 GATE READY
```

to `STATUS.md` and stop.

Do not begin PLAN-2.
